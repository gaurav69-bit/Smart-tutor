# Smart Tutor Week 4 database handoff (ST-104–ST-108)

## Environment (never commit `.env`)
Backend working directory: `apps/api`. Copy `.env.example` to `.env` and set the relevant values.

- Local SQLite (legacy): omit `DB_CLIENT` or use `DB_CLIENT=sqlite3`; the SQLite startup path stays unchanged.
- Local MySQL 8.4: `DB_CLIENT=mysql2`, `DB_HOST=127.0.0.1`, `DB_PORT=3306`, `DB_USER=<local user>`, `DB_PASSWORD=<private secret>`, `DB_NAME=<local database>`, `DB_SSL=false`.
- Hosted TiDB: supply the host, port, user, password, database and certificate authority from the owner. Use verified TLS (omit `DB_SSL=false`); set `DB_SSL_CA` if a custom CA is required. Never disable certificate verification to work around an invalid certificate.

## Running database migrations

From `apps/api`: run `npm run db:migrate` with `DB_CLIENT=mysql2` in the local `.env`. The server checks MySQL on startup but deliberately **does not** apply MySQL migrations automatically. Avoid running migrations on production databases until the schema is reviewed and backed up.

- `001_initial_schema` creates `users`.
- `002_account_identity_and_outbox` creates `account_profiles`, `account_secrets`, `email_verifications`, `sessions`, `auth_tokens`, and `email_outbox`.
- `003_account_states_and_delivery_audit` adds independent `users.approval_status` (pending/approved/rejected) and `users.email_verified_at`, plus `otp_challenges` and `email_delivery_attempts`.
- Applied migration names are recorded in `schema_migrations`. Re-running completed migrations makes no changes. If expected tables are missing or appear without a recorded migration, the runner stops rather than silently overwriting them.
- Do not use `db:seed` with MySQL: its current seed script is specifically for SQLite's synthetic development data.

## ST-106 persistence contracts for Jahid Hasan

Import from `apps/api/src/account-store.js`:
- `createAccount(db, {name, email, role, passwordHash, bio?})`: creates user, hashed password record and profile in one transaction. Requires a **pre-hashed** password generated by the authentication layer, e.g. Argon2id or bcrypt; it does not hash raw passwords.
- `findAccountByEmail(db, email)`: public account profile with independent `approval_status` and `email_verified_at` state; never returns password hashes.
- `findAccountCredentials(db, email)`: explicit credentials lookup for the authentication service; returned hash must never be included in an HTTP response.
- `updateAccountProfile(db, userId, {bio})`.
- `storeEmailVerification(db, {userId, token, expiresAt})`, `storeAuthToken(db, {userId, purpose, token, expiresAt})`, `createSession(db, {id, userId, expiresAt})`.
- `enqueueEmail(db, {userId?, recipient, subject, body})`, `getPendingEmails(db, limit?)`, `markEmailSent(db, id)`.
- `setAccountApproval(db, userId, status)`, `markEmailVerified(db, userId)`, `createOtpChallenge(db, {userId, purpose, code, expiresAt, hashSecret})`, and `recordEmailDeliveryAttempt(db, {outboxId, delivered, providerMessageId?, errorSummary?})`. The latter records a delivery attempt and updates the outbox in one transaction.

Token functions hash the tokens before persisting them. OTP challenges use keyed HMAC-SHA256 (via `fingerprintOtp(code, hashSecret)`) because six-digit codes cannot safely be stored as bare hashes. The caller must provide a high-entropy, private `hashSecret` (at least 32 characters), never commit it or store it in the database, and use the same key for OTP verification. Callers must create cryptographically unpredictable tokens and enforce expiry, one-time use, rate limits and session revocation. Email sending is **not** implemented here: the outbox records pending email only. Plan and confirm the registration/verification/login route contract with Jahid before changing endpoints.

**IMPORTANT:** `/api/sample/register-validation` and `/api/sample/login-validation` remain validation-only examples. They do **not** create accounts or authenticate users.

## ST-106 proposal for Jahid's PR #11 (not merged or wired)

The file `src/auth-persistence-adapters.js` exports `createAuthPersistenceAdapters(knexDb, { verifyPassword })` with the proposed async functions:
`registerAccount(account, validatedProfile)`, `consumeVerificationToken(tokenHash)`,
`authenticatePassword(normalizedEmail, password)`, `persistSession({accountId,tokenHash,expiresAt})`,
`lookupSession(tokenHash)`, and `revokeSession(tokenHash)`.

- Registration translates a database duplicate-key violation into `DUPLICATE_EMAIL` and stores only validated `bio`. **The team must still approve and implement any additional role-specific profile and consent fields before production registration can be enabled.**
- Verification consumes only valid, unexpired hashed tokens. Replay does not succeed. The user's `email_verified_at` is updated in the same transaction.
- Login uses a caller-supplied password verification function (Jahid's scrypt implementation) and requires both verified email and `approval_status=approved`. **The team must decide whether this approval gate applies to both roles or tutors only** before wiring to Express.
- Sessions store only the hashed opaque session token, support lookups/revocation, and reject unapproved accounts.
- The outbox resend workflow (`queueVerificationResend`) is **not included yet**. It requires an approved resend cooldown, token/URL lifecycle, eligible account policy, durable outbox link construction and coordinated mail delivery to avoid falsely claiming a working endpoint.

These are deliberately stand-alone adapters: PR #11 is owned by Jahid and remains unmerged. No code from PR #11 was copied into this branch, and `src/app.js` still exposes only the Week 3 sample validators. Automated tests cover the proposed DB interfaces against an isolated SQLite-backed Knex instance and, in CI, against a disposable real MySQL database.

## ST-106 independent outbox dispatch infrastructure (not enabled in production)

`src/outbox-dispatcher.js` exports `processPendingOutbox(knexDb, { send, limit? })`. It is **opt-in only**: no server, cron job, or route invokes it automatically, and it is not connected to Brevo or another live provider. Tests inject synthetic `send(message)` implementations. The transport must return an explicit `{ messageId: string }` to count as accepted.

- It selects pending messages and atomically claims each with a conditional `status='pending' -> 'sending'` update. Only the worker that wins the claim calls the injected transport. Completion updates the outbox and inserts a `email_delivery_attempts` audit entry in one database transaction.
- Accepted sends are marked `sent`; failures return to `pending` with a generic, credential-safe audit entry, and the attempt count increments. No provider exception is written to the database.
- If a worker crashes after claiming a row, or a provider accepts an email but persistence of the result fails, the row remains `sending` for **manual reconciliation**. It must not be automatically requeued because the external message may already have been delivered. This protects against unintentional duplicate sends but is **not** end-to-end exactly-once delivery.
- No backoff, cooldown, resend eligibility, max-attempt policy, automatic recovery, verification link generation, approval checks, or live delivery is claimed. Those behaviours need agreement with Gaurav and Jahid and a coordinated production worker design.
- Separate SQLite tests cover success, failure with redacted errors, explicit retry, concurrent claims, crash-state behaviour, and validation. The real MySQL CI integration test also runs an isolated synthetic-transport dispatch and checks the durable audit.

## Approval Pending — ST-106 verification resend preparation

`src/verification-outbox-adapter.js` exports the opt-in `createVerificationResendAdapter(db, options)`. The caller MUST inject an approved random token generator (`createToken`), message renderer (`renderVerificationEmail`), token expiry and cooldown before the adapter can be constructed. The adapter returns one `queueVerificationResend(normalizedEmail)` function compatible with the proposed PR #11 HTTP boundary but is **not wired to the application**.

For an eligible unverified account, the adapter locks the user's row on MySQL, checks the latest recorded verification issue time, and atomically stores a SHA-256 verification token digest plus the queued email. Unknown, already verified or cooldown-blocked accounts yield the same generic result. Builder failures roll back both writes. An actual API handler must still use the same generic 202 response for all eligible/ineligible accounts and enforce request rate limits. **The outbox body necessarily contains the verification URL and must be treated as sensitive application data**, protected through database access controls and retention policies.

This is a policy-neutral infrastructure component, not production signup/email functionality. Pending decisions include student/tutor profile and consent schema, when the initial registration challenge is issued, allowed verification URL/base domain and token TTL, resend cooldown, delivery retry policy, session/cookie settings, live sender credentials, hosted TiDB and the actual frontend flow. Tests use only synthetic tokens and addresses. GitHub CI checks the transactional implementation on disposable SQLite and MySQL 8.4. New teammates' PRs #13 and #15 provide **separate integration demonstrations under Approval Pending**; those branches are not merged or modified here.

**Approval Pending** remains the official status of ST-104 to ST-108 and PR #12 until peer review and required production/hosted verification.
