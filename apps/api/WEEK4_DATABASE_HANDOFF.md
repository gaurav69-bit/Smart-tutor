# Smart Tutor Week 4 database handoff (ST-104–ST-108)

## Environment (never commit `.env`)
Backend working directory: `apps/api`. Copy `.env.example` to `.env` and set the relevant values.

- Local SQLite (legacy): omit `DB_CLIENT` or use `DB_CLIENT=sqlite3`; the SQLite startup path stays unchanged.
- Local MySQL 8.4: `DB_CLIENT=mysql2`, `DB_HOST=127.0.0.1`, `DB_PORT=3306`, `DB_USER=<local user>`, `DB_PASSWORD=<private secret>`, `DB_NAME=<local database>`, `DB_SSL=false`.
- Hosted TiDB: supply the host, port, user, password, database and certificate authority from the owner. Use verified TLS (omit `DB_SSL=false`); set `DB_SSL_CA` if a custom CA is required. Never disable certificate verification to work around an invalid certificate.

## Running database migrations

From `apps/api`: run `npm run db:migrate` with `DB_CLIENT=mysql2` in the local `.env`. The server checks MySQL on startup but deliberately **does not** apply MySQL migrations automatically. Avoid running migrations on production databases until the schema is reviewed and backed up.

- `001_initial_schema` creates `users`.
- `002_account_identity_and_outbox` creates `account_profiles`, `account_secrets`, `email_verifications`, `sessions`, `auth_tokens`, and `email_outbox`.
- `003_account_states_and_delivery_audit` adds independent `users.approval_status` (pending/approved/rejected) and `users.email_verified_at`, plus `otp_challenges` and `email_delivery_attempts`.
- Applied migration names are recorded in `schema_migrations`. Re-running completed migrations makes no changes. If expected tables are missing or appear without a recorded migration, the runner stops rather than silently overwriting them.
- Do not use `db:seed` with MySQL: its current seed script is specifically for SQLite's synthetic development data.

## ST-106 persistence contracts for Jahid Hasan

Import from `apps/api/src/account-store.js`:
- `createAccount(db, {name, email, role, passwordHash, bio?})`: creates user, hashed password record and profile in one transaction. Requires a **pre-hashed** password generated by the authentication layer, e.g. Argon2id or bcrypt; it does not hash raw passwords.
- `findAccountByEmail(db, email)`: public account profile; never returns password hashes.
- `findAccountCredentials(db, email)`: explicit credentials lookup for the authentication service; returned hash must never be included in an HTTP response.
- `updateAccountProfile(db, userId, {bio})`.
- `storeEmailVerification(db, {userId, token, expiresAt})`, `storeAuthToken(db, {userId, purpose, token, expiresAt})`, `createSession(db, {id, userId, expiresAt})`.
- `enqueueEmail(db, {userId?, recipient, subject, body})`, `getPendingEmails(db, limit?)`, `markEmailSent(db, id)`.
- `setAccountApproval(db, userId, status)`, `markEmailVerified(db, userId)`, `createOtpChallenge(db, {userId, purpose, code, expiresAt})`, and `recordEmailDeliveryAttempt(db, {outboxId, delivered, providerMessageId?, errorSummary?})`. The latter records a delivery attempt and updates the outbox in one transaction.

Token functions hash the tokens before persisting them. Callers must create cryptographically unpredictable tokens and enforce expiry, one-time use, rate limits and session revocation. Email sending is **not** implemented here: the outbox records pending email only. Plan and confirm the registration/verification/login route contract with Jahid before changing endpoints.

**IMPORTANT:** `/api/sample/register-validation` and `/api/sample/login-validation` remain validation-only examples. They do **not** create accounts or authenticate users.
